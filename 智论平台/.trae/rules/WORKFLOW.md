# 智论平台 - 开发工作流

> 版本：1.0.0  
> 更新日期：2026-05-09  
> 用途：定义智论平台的开发流程和协作机制

---

## 📋 工作流概览

智论平台采用**分级开发流程**，根据功能优先级（P0/P1/P2）采用不同的开发步骤，确保开发效率和质量。

### 核心原则

1. **分级流程** - 不同优先级功能采用不同流程
2. **主从协作** - 主责Agent主动召唤协作Agent
3. **人类终审** - 您保留最终决策权
4. **数据驱动** - Schema变更决定流程等级

## 🔄 分级开发流程

### P0功能：完整五步流程

**适用场景：**
- 涉及核心算法变更
- 用户付费功能
- 数据库Schema变更

**流程步骤：**

```
┌─────────────────────────────────────────────────────────┐
│ 步骤1：需求准入                                          │
│ ProductAgent输出PRD → 人类总监批准                       │
└────────────────┬────────────────────────────────────────┘
                 │
┌────────────────▼────────────────────────────────────────┐
│ 步骤2：技术对齐                                          │
│ ArchitectAgent输出技术规格 → 人类总监批准                 │
└────────────────┬────────────────────────────────────────┘
                 │
┌────────────────▼────────────────────────────────────────┐
│ 步骤3：并行开发                                          │
│ BackendAgent + FrontendAgent + AIEngineerAgent           │
└────────────────┬────────────────────────────────────────┘
                 │
┌────────────────▼────────────────────────────────────────┐
│ 步骤4：集成验证                                          │
│ TestAgent自动化测试 → 人类总监验收指标                    │
└────────────────┬────────────────────────────────────────┘
                 │
┌────────────────▼────────────────────────────────────────┐
│ 步骤5：审查交付                                          │
│ ArchitectAgent代码审查 → DevOpsAgent部署                  │
└─────────────────────────────────────────────────────────┘
```

**详细步骤说明：**

#### 步骤1：需求准入

**触发条件：** 您发出新功能开发指令

**执行流程：**

```
你：@ProductAgent 请基于《智论平台_产品方案_V1.0》中【3.1 论文去重与AIGC降痕】的定义，为我输出"论文降重-MVP版本"的PRD片段。要求：

1. 明确本次MVP的用户故事（As a... I want... so that...）
2. 列出功能清单与验收标准（每个功能必须有可量化的成功指标）
3. 标注本期明确不做的内容（防止范围蔓延）

上下文：目标用户为高校应届毕业生，他们提交论文终稿前需要进行查重预检和降重处理。
```

**验收动作：** 您阅读PRD后，确认边界清晰，回复"批准"。

#### 步骤2：技术对齐

**触发条件：** PRD获得批准

**执行流程：**

```
你：@ArchitectAgent 基于以下被批准的PRD，输出本功能的技术规格文档。要求：

1. API接口定义（路径、请求/响应结构、错误码）
2. 数据库Schema变更（若有，须提供Prisma schema格式）
3. 前端组件树与数据流
4. Agent调用链路设计（谁调用谁，超时与降级策略）
5. 安全性考量（参数校验、SQL注入防护、限流策略）

[粘贴ProductAgent的PRD]
```

**验收动作：** 逐项检查API是否满足需求、数据库设计是否合理。确认后回复"批准，按此规格开发"。

#### 步骤3：并行开发

**触发条件：** 技术规格获得批准

**执行流程：**

```
你：@BackendAgent 请严格按以下技术规格实现后端服务。要求：
- 框架使用Fastify + TypeScript，禁止使用any类型
- 所有API必须包含OpenAPI Swagger注释
- 数据库操作使用Prisma参数化查询
- 错误统一使用AppError类处理
- 实现输入参数的严格校验

[粘贴技术规格文档中"后端"部分]

你：@FrontendAgent 请严格按以下技术规格实现前端页面。要求：
- 使用Next.js 14 + shadcn/ui组件库
- 实现完整的加载、空状态、错误状态处理
- 移动端响应式适配
- 所有用户操作须有即时反馈（loading/disabled状态）

[粘贴技术规格文档中"前端"部分]

你：@AIEngineerAgent 请严格按以下技术规格设计AI改写策略。要求：
1. 设计改写Prompt模板（至少3个变体，用于A/B测试）
2. 定义改写参数结构（强度、风格、专有名词保护清单）
3. 设计降重率实时监控的触发阈值与熔断策略
4. 输出改写质量评估脚本的思路

[粘贴技术规格文档中"AI策略"部分]
```

**验收动作：** 三个Agent产出后，暂不深度审查，直接进入集成。

#### 步骤4：集成验证

**触发条件：** 代码开发完成

**执行流程：**

```
你：请将以下代码集成到项目，确保前后端接口对齐，错误处理完整：
[粘贴BackendAgent的API代码]
[粘贴FrontendAgent的组件代码]
[粘贴AIEngineerAgent的Prompt配置]

你：@TestAgent 请基于以下技术规格中的验收标准，为本次集成的功能生成自动化测试。要求：
1. 单元测试针对核心业务逻辑，覆盖率≥80%
2. 集成测试覆盖完整API请求-响应链路
3. E2E测试覆盖核心用户操作路径
4. 专项测试：降重率回归测试（确保改写后降重率达标）
5. 边界测试：空文本、超长文本、特殊字符输入

[粘贴技术规格文档]

生成测试后请立即运行，输出测试报告，标注所有失败案例。
```

**验收动作：** 这是最重要的决策点。只看TestAgent的报告：
- 全部通过 → 进入下一步
- 有失败 → 指派对应Agent修复，重新跑测试，直到通过

#### 步骤5：审查交付

**触发条件：** 测试全部通过

**执行流程：**

```
你：@ArchitectAgent 请对本次功能进行最终代码审查。审查范围包括：
1. 安全性（SQL注入、XSS、未授权访问）
2. 性能（N+1查询、未索引字段、缓存策略）
3. 可维护性（代码重复、过长函数、Magic Number）
按"严重/警告/建议"三级标准输出审查报告。
```

**处理审查结果：**
- 严重问题 → 指派Agent立即修复，修复后重新跑TestAgent测试
- 警告 → 记录到技术债务清单，本阶段可接受
- 建议 → 文档记录，后续迭代处理

```
你：@DevOpsAgent 请将当前通过全部测试和审查的代码部署到预发布环境。要求：
1. 执行数据库迁移脚本
2. 配置环境变量与密钥（使用Vault）
3. 验证健康检查端点
4. 配置监控告警规则（API响应时间>3s触发告警）
```

### P1功能：四步流程

**适用场景：**
- 新增接口或新页面组件
- 不影响核心算法与数据模型
- Schema不变

**流程步骤：**

```
┌─────────────────────────────────────────────────────────┐
│ 步骤1：技术规格                                          │
│ ArchitectAgent直接输出"技术规格+验收标准"                 │
│ （跳过单独PRD，但技术规格中须包含功能说明）                │
│ → 人类总监批准                                          │
└────────────────┬────────────────────────────────────────┘
                 │
┌────────────────▼────────────────────────────────────────┐
│ 步骤2：并行开发                                          │
│ BackendAgent + FrontendAgent                             │
└────────────────┬────────────────────────────────────────┘
                 │
┌────────────────▼────────────────────────────────────────┐
│ 步骤3：测试验证                                          │
│ TestAgent核心路径测试 → 人类总监验收                      │
└────────────────┬────────────────────────────────────────┘
                 │
┌────────────────▼────────────────────────────────────────┐
│ 步骤4：审查部署                                          │
│ ArchitectAgent代码审查 → DevOpsAgent部署                  │
└─────────────────────────────────────────────────────────┘
```

**P1升级规则：**

在P1流程中，如果ArchitectAgent在出技术规格时发现：
- 需要修改数据库Schema
- 需要新增第三方API调用
- 会影响已有核心功能的行为

则自动升级为P0，补上ProductAgent的PRD环节。

**指令示例：**

```
你：@ArchitectAgent 请为"新增文献导入源适配器"功能输出技术规格。要求：
1. API接口定义
2. 前端组件设计
3. 验收标准
注意：这是P1功能，Schema不变，如果发现需要Schema变更请立即告知我。
```

### P2功能：三步流程

**适用场景：**
- 纯展示层变更
- 文案修改
- 已有接口的非破坏性调整

**流程步骤：**

```
┌─────────────────────────────────────────────────────────┐
│ 步骤1：直接开发                                          │
│ FrontendAgent/BackendAgent直接实现                       │
│ （你口头描述需求即可）                                    │
└────────────────┬────────────────────────────────────────┘
                 │
┌────────────────▼────────────────────────────────────────┐
│ 步骤2：基础测试                                          │
│ TestAgent冒烟测试（只测不崩溃+核心路径）                  │
└────────────────┬────────────────────────────────────────┘
                 │
┌────────────────▼────────────────────────────────────────┐
│ 步骤3：直接部署                                          │
│ DevOpsAgent部署                                          │
└─────────────────────────────────────────────────────────┘
```

**指令示例：**

```
你：@FrontendAgent 请优化登录页面的文案，将"欢迎登录"改为"欢迎回来，开始您的学术之旅"。
```

## 🎯 任务分级判断标准

### 快速判断流程

```
开始
  │
  ├─ 是否涉及数据库Schema变更？
  │   ├─ 是 → P0（完整五步）
  │   └─ 否 ↓
  │
  ├─ 是否涉及核心算法变更？
  │   ├─ 是 → P0（完整五步）
  │   └─ 否 ↓
  │
  ├─ 是否涉及用户付费功能？
  │   ├─ 是 → P0（完整五步）
  │   └─ 否 ↓
  │
  ├─ 是否新增接口或新页面组件？
  │   ├─ 是 → P1（四步流程）
  │   └─ 否 ↓
  │
  └─ 是否纯展示层变更？
      ├─ 是 → P2（三步流程）
      └─ 否 → 重新评估
```

### 一句话执行原则

**"数据不动随便改，数据一动走全套。"**

- Schema不变 → P1起步
- Schema要变 → 一律P0

## 🚨 异常处理流程

### 测试失败处理

```
TestAgent报告失败
  │
  ├─ 分析失败原因
  │   ├─ 代码逻辑错误 → 指派对应Agent修复
  │   ├─ 接口不匹配 → ArchitectAgent协调
  │   └─ 环境问题 → DevOpsAgent处理
  │
  └─ 修复后重新测试
      └─ 直到全部通过
```

### 技术债务处理

```
发现技术债务
  │
  ├─ 严重级别
  │   └─ 立即修复，暂停新功能开发
  │
  ├─ 警告级别
  │   └─ 记录到技术债务清单，本周内修复
  │
  └─ 建议级别
      └─ 文档记录，后续迭代处理
```

### 需求变更处理

```
需求变更
  │
  ├─ 评估影响范围
  │   ├─ 影响Schema → 重新走P0流程
  │   ├─ 影响核心功能 → 重新走P0流程
  │   └─ 仅影响展示层 → 走P2流程
  │
  └─ 更新文档
      ├─ 更新产品方案
      └─ 更新技术方案
```

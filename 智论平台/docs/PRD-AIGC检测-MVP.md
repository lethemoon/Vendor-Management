## 1. 功能概述

### 1.1 功能定位

AIGC检测与降痕是智论平台P0核心功能，定位为**面向中文学术场景的一站式AIGC风险管控工具**。该功能独立于已完成的论文降重功能，专注于解决用户在使用AI辅助写作后面临的AIGC检测风险问题。

**核心定位差异（vs 论文降重）：**
- 论文降重：解决与已有文献的重复率问题
- AIGC降痕：解决被检测系统判定为AI生成的问题
- 两者互补但不重叠，用户可能同时需要两项服务

### 1.2 目标用户

| 用户群体 | 核心需求 | 使用频率 | 付费意愿 |
|---------|---------|---------|---------|
| 本科毕业生 | 毕业论文AIGC检测+降痕 | 高（毕业季） | 中 |
| 硕士研究生 | 学位论文多轮优化 | 中高 | 高 |
| 博士研究生 | 学术发表前自检 | 中 | 高 |
| 高校教师 | 学生作业审核 | 低 | 低 |

**典型用户画像：**
- 李同学，22岁，大四学生，正在撰写毕业论文，使用ChatGPT辅助生成部分章节内容，担心学校使用的知网AIGC检测系统标记其论文
- 张博士，27岁，研二学生，需要投稿核心期刊，期刊要求提供AIGC检测报告，需要在提交前降低AIGC疑似率

### 1.3 核心价值主张

**解决的痛点：**
1. **检测焦虑**：用户不确定自己的文本是否会被AIGC检测系统标记
2. **改写盲目**：不知道如何针对性修改才能有效降低AIGC率
3. **效率低下**：手动逐句修改耗时巨大且效果不可预测
4. **成本高昂**：商业检测平台单次检测费用高（10-50元/次）

**带来的价值：**
1. **一站式闭环**：检测→分析→改写→复测全流程自动化
2. **精准定位**：段落级检测结果，明确指出高风险区域
3. **智能改写**：基于对抗性策略的AI改写，而非简单的同义词替换
4. **效果可视**：实时预估改写后的AIGC率变化，避免无效劳动
5. **成本可控**：相比商业平台降低60%以上的检测改写成本

## 2. 用户故事

### 2.1 主用户故事

**作为** 一名使用过AI工具辅助写作的高校学生，

**我希望** 上传我的论文文本后，系统能自动识别出哪些段落可能被AIGC检测系统标记为AI生成，并针对这些段落提供智能化的改写建议，

**以便于** 我能够在正式提交论文前有效降低AIGC检测风险，顺利通过学校的学术诚信审查。

**验收标准 (AC)：**

- **AC-1: 基础检测**
  - Given 用户已登录系统并拥有有效的字数配额
  - When 用户在AIGC检测页面粘贴或导入100-50000字的中文论文文本
  - Then 系统应在5秒内返回检测结果，包含总体AIGC疑似率和段落级分析结果

- **AC-2: 结果可视化**
  - Given 系统已完成AIGC检测分析
  - When 用户查看检测结果页面
  - Then 页面应展示：(a)圆形进度条显示总体AIGC率 (b)段落热力图标识各段风险等级 (c)问题类型标签统计

- **AC-3: 对抗改写**
  - Given 用户查看到存在高风险段落（疑似度≥60%）的检测结果
  - When 用户选择一个或多个高风险段落并点击"智能降痕"按钮
  - Then 系统应在8秒内生成2-3个改写版本，每个版本显示预估的新AIGC率和置信度评分

- **AC-4: 多轮优化**
  - Given 用户已完成第一轮改写操作
  - When 用户点击"重新检测"按钮
  - Then 系统应基于更新后的文本重新计算AIGC率，并与历史结果对比显示变化趋势

- **AC-5: 历史追溯**
  - Given 用户进行了多次检测和改写操作
  - When 用户访问历史记录页面
  - Then 系统应按时间倒序展示所有操作记录，支持查看任意一次的详细结果

**检测算法思路（MVP）：**

采用**规则引擎 + LLM辅助判断**的混合方案，兼顾响应速度和检测准确度：

**第一层：规则引擎快速筛选（权重40%）**

基于语言学特征的启发式规则：

1. **困惑度代理指标**（Perplexity Proxy）：
   - 计算文本的词汇多样性指数（Type-Token Ratio, TTR）
   - AI文本TTR通常较低（0.3-0.5），人类文本较高（0.5-0.7）
   - 公式：`TTR = unique_words / total_words`

2. **句长方差分析**（Burstiness Proxy）：
   - AI生成的句子长度趋于均匀（方差小）
   - 人类写作句长变化大（方差大）
   - 计算：`sentence_length_variance = var([len(s) for s in sentences])`
   - 阈值：方差 < 15 → 高疑似；15-30 → 中疑似；> 30 → 低疑似

3. **高频AI词汇检测**：
   - 维护一份AI常用词汇表（约200词）
   - 包括：综上所述、由此可见、值得注意的是、不难发现、首先...其次...最后...
   - 统计这些词汇的出现频率密度（每千字出现次数）
   - 密度 > 5次/千字 → 扣分

4. **过渡词模式匹配**：
   - 检测典型的AI过渡模式："一方面...另一方面"、"不仅...而且..."
   - 使用正则表达式匹配固定搭配

5. **被动语态比例**：
   - AI文本倾向于更多使用被动语态
   - 统计"被...所..."、"由...构成"等被动句式占比

**第二层：LLM精细判断（权重60%）**

对于规则引擎筛选出的可疑段落，调用DeepSeek API进行二次确认：

```python
# 伪代码示意
def llm_aigc_detect(paragraph: str) -> tuple[float, list[str]]:
    prompt = f"""
    你是一个专业的AIGC文本检测器。请分析以下文本段落，判断其为AI生成的可能性。
    
    要求：
    1. 返回0-100的疑似度分数
    2. 列出具体的AI写作特征证据（最多3个）
    
    文本内容：
    {paragraph}
    
    请以JSON格式输出：{{"score": <0-100>, "evidence": ["特征1", "特征2"]}}
    """
    response = call_deepseek_api(prompt)
    return parse_json(response)
```

**综合评分公式：**

```
final_score = rule_score * 0.4 + llm_score * 0.6

其中：
- rule_score: 规则引擎得分（0-100）
- llm_score: LLM判断得分（0-100）
```

#### 3.2.2 对抗性改写策略

**核心理念：**

对抗性改写的目标是**打破AIGC检测算法能够识别的模式特征**，而非简单地同义词替换。改写需要让文本呈现出更接近人类自然写作的特征，同时保持学术规范性。

**改写原则：**

1. **打破AI写作模式**（最重要）
   - 打破均匀的句式节奏
   - 减少程式化的过渡表达
   - 引入适度的"不完美"

2. **增加人类写作特征**
   - 加入个人化表达（笔者认为、据笔者观察）
   - 使用口语化连接词（话说回来、换个角度看）
   - 允许一定的主观判断表述

3. **保持学术规范性**（底线约束）
   - 专业术语不能随意替换
   - 引用格式保持正确
   - 逻辑链条不能断裂
   - 数据和事实陈述保持准确

4. **保护核心语义**（质量保证）
   - 改写前后语义相似度 ≥ 85%（使用BERT计算）
   - 关键论点和结论不能改变
   - 学科特定概念保持一致

**改写技术详解：**

**技术1：句式多样化重组**

```python
# 原文（AI风格 - 句式均匀）
"""
本研究采用实验方法，首先收集数据，然后进行分析，最后得出结论。
"""

# 改写后（人类风格 - 句式长短交替）
"""
为了验证研究假设，我们设计了一套系统的实验方案——数据采集工作持续了两周；
紧接着，借助SPSS软件对这些原始数据展开了多维度统计分析；
最终，实验结果清晰地指向了预设的研究结论。
"""
```

具体操作：
- 将短句合并为长句（增加从句、插入语）
- 将长句拆分为短句（增加停顿感）
- 调整语序（倒装、前置、后置）
- 增加标点变化（破折号、括号补充说明）

**技术2：词汇个性化替换**

维护一份**AI高频词汇 → 人类替代表**（示例）：

| AI高频词 | 替换选项（随机选取） |
|---------|-------------------|
| 综上所述 | 归根结底 / 总的来说 / 回顾整项研究 |
| 值得注意的是 | 需要特别指出的是 / 有趣的是 / 一个关键的发现是 |
| 不难发现 | 我们观察到 / 数据显示 / 结果表明 |
| 首先...其次...最后 | 第一点...在此基础上...最终 / 先来看...接着...至于 |
| 具有...意义 | 意味着... / 这说明... / 从这个角度看... |

     └──────────────┘   └──────────────┘
                              │
                              └──────→ 循环
```

**每轮优化的改进目标与策略：**

| 轮次 | 目标AIGC率 | 重点关注 | 推荐操作 |
|-----|-----------|---------|---------|
| 初始状态 | 基线值 | 全面摸底 | 无 |
| 第1轮 | 降低15-25% | 所有高分段落（>60%） | 采用平衡型改写 |
| 第2轮 | 降低10-15% | 剩余中高分段落（40-60%） | 针对性选择改写风格 |
| 第3轮 | 降低5-10% | 边界段落（30-40%） | 微调+局部重写 |
| 第4轮+ | <20%达标 | 个别顽固段落 | 激进型改写或人工介入 |

**配额消耗机制：**

| 操作类型 | 配额消耗 | 说明 |
|---------|---------|------|
| 初始检测 | 1x字数 | 按实际文本字数计算 |
| 单段改写 | 0.5x段字数 | 每段改写消耗该段字数的50% |
| 复测验证 | 0.3x总字数 | 复测享受折扣优惠 |
| 重新生成 | 0.5x段字数 | 与正常改写相同 |

**优化上限保护：**

- 单篇文档最多支持 **10轮** 优化操作
- 超过后提示："已达最大优化轮次，建议保存当前结果后新建任务"
- 目的：防止无限循环导致配额耗尽和文本过度修改

**状态机定义：**

```
[DRAFT] --提交检测--> [ANALYZING] --完成--> [ANALYZED]
                                              |
                                    选择段落+改写 --> [OPTIMIZING]
                                              |
                                    应用改写+复测 --> [RECHECKING]
                                              |
                                     +----达标---> [COMPLETED]
                                     |
                                     +----未达标--+--> [ANALYZED] (循环)
```

**历史记录存储结构：**

每次优化操作都会生成一条 `OptimizationRecord` 记录：

```typescript
interface OptimizationRecord {
  id: string;
  detectionId: string;
  roundNumber: number;           // 第几轮优化
  operationType: 'initial_detect' | 'rewrite' | 'recheck';
  
  // 操作前状态
  beforeAigcRate: number;
  beforeParagraphsCount: number;
  
  // 操作详情
  targetParagraphIndices: number[];  // 操作了哪些段落
  selectedVersion: 'A' | 'B' | 'C';  // 选择了哪个版本
  rewriteTexts: string[];            // 改写后的文本片段
  
  // 操作后状态
  afterAigcRate: number;
  rateChange: number;                // 变化量（正数表示上升，负数表示下降）
  
  // 元数据
  processingTimeMs: number;
  tokensConsumed: number;
  costCredits: number;
  
  createdAt: Date;
}

## 5. 非功能性需求

### 5.1 性能要求

| 场景 | 响应时间 | 吞吐量 | 并发支持 | 备注 |
|-----|---------|--------|---------|------|
| 文本上传与校验 | <1s | 100 req/s | 50并发 | 本地校验，无API调用 |
| AIGC检测（5000字） | <5s | 50 req/s | 20并发 | 含规则引擎+LLM调用 |
| AIGC检测（20000字） | <12s | 30 req/s | 10并发 | 长文本需分段处理 |
| 单段改写（500字） | <8s | 30 req/s | 20并发 | LLM生成+后处理 |
| 三段批量改写 | <15s | 20 req/s | 10并发 | 并行调用LLM API |
| 复测验证 | <5s | 50 req/s | 20并发 | 增量检测，仅重算变更段落 |
| 历史记录查询 | <2s | 100 req/s | 50并发 | 数据库查询 |
| 报告导出（P1） | <3s | 80 req/s | 30并发 | PDF生成 |

**性能优化策略：**

1. **前端优化**：
   - 虚拟滚动渲染长文本（>5000字时启用）
   - 懒加载段落详情（仅渲染可视区域）
   - 骨架屏占位（检测期间）
   - 防抖输入（文本框输入时不频繁触发校验）

2. **后端优化**：
   - Redis缓存热门检测结果（相同文本hash命中则直接返回）
   - 检测结果增量更新（复测时只重算修改过的段落）
   - LLM API调用异步化（使用消息队列）
   - 连接池管理数据库连接

3. **API优化**：
   - 流式SSE返回改写结果（首token延迟<2s）
   - 请求压缩（gzip）
   - CDN缓存静态资源

### 5.2 准确性要求

| 指标 | MVP目标 | P1目标 | 测量方法 |
|-----|---------|--------|---------|
| AIGC检测准确率 | ≥75% | ≥85% | 人工标注测试集（500样本） |
| 误报率（人工判为AI但误报） | ≤20% | ≤10% | 同上 |
| 漏报率（AI文本未检出） | ≤15% | ≤8% | 同上 |
| 改写后AIGC率降低（平均） | ≥25% | ≥35% | 改写前后对比统计 |
| 改写语义保持度 | ≥82% | ≥90% | BERT语义相似度计算 |
| 改写通顺度（人工评分） | ≥3.5/5.0 | ≥4.2/5.0 | 专家评审 |

**准确性保障措施：**

1. **测试集建设**：
   - 收集100篇真实AI生成文本（GPT-4/Claude/DeepSeek各1/3）
   - 收集100篇真实人类写作文本（学术论文）
   - 混合打乱后建立500样本的黄金测试集
   - 每月更新测试集以应对检测算法进化

2. **持续监控**：
   - 生产环境抽样回测（每日随机抽取5%的结果人工复核）
   - 用户反馈渠道（"检测结果不准确"举报按钮）
   - 准确率仪表盘（实时展示各项指标趋势）

3. **算法迭代机制**：
   - 每周分析误报/漏报案例
   - 调整规则权重和Prompt模板
   - 月度发布算法版本更新

### 5.3 安全与隐私

### 6.3 存储数据模型（扩展现有Schema）

**方案：扩展现有 Paper 表 + 新增 AIGCDetection 表 + 新增 OptimizationRecord 表**

```prisma
// ========== 扩展现有的 Paper 表 ==========
// 已有以下字段可直接复用：
// - aigcRate: Float?          → 存储最新的AIGC率
// - processedText: String?    → 存储优化后的文本
// - status: PaperStatus       → 复用状态枚举

// 新增字段（通过migration添加）：
model Paper {
  // ... 现有字段保持不变 ...
  
  // 新增AIGC相关字段
  aigcDetectionId     String?           // 关联最新的一次AIGC检测
  aigcOptimizationRounds Int      @default(0)  // 已完成的优化轮次
  aigcInitialRate      Float?           // 初始AIGC率（用于计算降幅）
  
  // 新增关联关系
  aigcDetections       AIGCDetection[]
  optimizationRecords  OptimizationRecord[]
  
  @@map("papers")
}

// ========== 新增：AIGC检测记录表 ==========
model AIGCDetection {
  id                  String            @id @default(uuid())
  userId              String
  paperId             String?           // 关联Paper表（可选，支持独立检测）
  title               String            // 论文标题
  
  // 原始内容（加密存储）
  contentHash         String            @unique   // 内容哈希（用于去重和缓存）
  encryptedContent    String?           @db.Text  // AES加密的完整内容（可选存储）
  
  // 检测结果（JSON存储，灵活schema）
  result              Json              // 完整的检测结果JSON
  
  // 快照字段（便于查询和排序）
  overallScore        Float
  riskLevel           AIGCRiskLevel
  paragraphCount      Int
  highRiskCount       Int               // 高风险段落数量（score>60）
  
  // 状态跟踪
  status              AIGCDetectionStatus @default(Pending)
  
  // 元数据
  processingTimeMs    Int               // 处理耗时（毫秒）
  creditsConsumed     Int               // 消耗的配额
  source              DetectionSource   @default(Paste)
  
  createdAt           DateTime          @default(now())
  updatedAt           DateTime          @updatedAt
  
  // 关联
  user                User              @relation(fields: [userId], references: [id], onDelete: Cascade)
  paper               Paper?            @relation(fields: [paperId], references: [id], onDelete: SetNull)
  optimizations       OptimizationRecord[]
  
  @@map("aigc_detections")
}

enum AIGCRiskLevel {
  Low
  Medium
  MediumHigh
  High
}

enum AIGCDetectionStatus {
  Pending            // 等待处理
  Analyzing          // 分析中
  Analyzed           // 分析完成
  Optimizing         // 优化中
  Completed          // 已完成（达标）
  Abandoned          // 已放弃
}

enum DetectionSource {
  Paste              // 粘贴输入
  FileImport         // 文件导入
  PaperLinked        // 从Paper关联
}

// ========== 新增：优化操作记录表 ==========
model OptimizationRecord {
  id                    String              @id @default(uuid())
  detectionId           String
  roundNumber           Int                 // 第几轮优化（从1开始）
  operationType         OptimizationType
  
  // 操作前快照
  beforeAigcRate        Float
  beforeTextHash        String              // 操作前的文本哈希
  
  // 操作详情
  targetParagraphIndices Int[]              // 操作了哪些段落索引
  selectedVersion       String?             // 选择的版本ID ('A'/'B'/'C')
  rewriteVersionIds      String[]            // 生成的所有版本ID列表
  
  // 操作后结果
  afterAigcRate         Float
  rateChange            Float               // 变化量
  
  // 资源消耗
  processingTimeMs      Int
  tokensConsumed        Int                 @default(0)
  costCredits           Int                 @default(0)
  
  // 详细记录（JSON）
  detail                Json?               // 包含改写前后的完整文本diff等
  
  createdAt             DateTime            @default(now())
  
  // 关联
  detection             AIGCDetection       @relation(fields: [detectionId], references: [id], onDelete: Cascade)
  
  @@map("optimization_records")
  @@index([detectionId, roundNumber])       // 复合索引：按检测ID和轮次查询
}

enum OptimizationType {
  InitialDetect         // 初始检测
  Rewrite               // 改写操作
  Recheck               // 复测验证
  ManualEdit            // 手动编辑（未来支持）
}
```

**数据库迁移注意事项：**

1. **向后兼容**：新增字段全部设置默认值或nullable，不影响现有数据
2. **索引优化**：为高频查询路径添加复合索引
   - `(userId, createdAt)` 用于历史记录列表
   - `(detectionId, roundNumber)` 用于优化时间线
   - `(contentHash)` 用于检测去重
3. **数据清理策略**：
   - 30天前的Abandoned状态记录自动归档
   - 90天前的Completed状态记录移至冷存储
   - encryptedContent字段在记录完成后可选择性清除以节省空间

**竞品核心洞察：**
1. 市场上"检测"和"改写"通常是分离的两个产品，**一体化是蓝海机会**

### E. UI设计规范摘要

为确保与现有论文降重页面保持一致的设计语言，遵循以下规范：

**色彩系统：**

| 用途 | 色值 | 说明 |
|-----|------|------|
| 主色调 | #3B82F6 (blue-500) | 按钮、链接、高亮 |
| 成功色 | #22C55E (green-500) | AIGC率安全、操作成功 |
| 警告色 | #EAB308 (yellow-500) | 中等风险 |
| 危险色 | #EF4444 (red-500) | 高风险、错误提示 |
| 背景色 | #F8FAFC (slate-50) | 页面背景 |
| 卡片背景 | #FFFFFF | 内容区域 |
| 文字主色 | #1E293B (slate-800) | 标题、正文 |
| 文字次要 | #64748B (slate-500) | 辅助说明 |

**字体规范：**

- 标题：Inter/System Font, Semibold, 1.25rem-2rem
- 正文：Inter/System Font, Regular, 0.875rem-1rem
- 代码/数据：JetBrains Mono/Monospace, 0.875rem
- 行高：1.5-1.75（正文），1.2（标题）

**间距系统：**

- 基础单位：4px
- 组件内间距：16px (gap-4)
- 区块间间距：24px (gap-6)
- 页面边距：24px桌面端 / 16px移动端

**圆角规范：**

- 按钮：8px (rounded-lg)
- 卡片：12px (rounded-xl)
- 输入框：8px (rounded-lg)
- 标签/徽章：9999px (rounded-full)

**动效规范：**

- 过渡时长：150ms（微交互）/ 300ms（状态变化）/ 500ms（页面切换）
- 缓动函数：ease-out（进入）/ ease-in（退出）
- 避免弹性/弹簧效果（学术产品应稳重）
